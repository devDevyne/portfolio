# 개발자 포트폴리오 웹페이지 계획

## 1. 프로젝트 개요

업무 및 개인 프로젝트의 결과를 단순한 기술·커밋 목록이 아니라 **문제 해결 과정, 설계 판단, 담당 범위와 기여** 중심으로 보여주는 개발자 포트폴리오 웹사이트를 만든다.

- 무엇을 만들었는가
- 어떤 문제를 해결했는가
- 어떤 점을 고려했는가
- 왜 해당 방식으로 설계·구현했는가
- 결과적으로 어떤 범위에 기여했는가

회사 프로젝트는 공개 범위를 검토하고 익명화한 뒤 공개한다. 회사 소스 코드, 내부 URL, 서버 정보, 고객 개인정보, API 키와 공개 허가를 받지 않은 자료는 포함하지 않는다.

## 2. 목표 사용자와 핵심 경험

### 주요 사용자

- 채용 담당자 및 기술 면접관
- 함께 일할 개발자와 기획자
- 프로젝트의 문제 해결 과정을 확인하려는 방문자

### 핵심 경험

방문자가 첫 화면에서 개발자의 정체성과 강점을 빠르게 파악하고, 관심 있는 프로젝트만 단계적으로 깊게 살펴볼 수 있어야 한다.

1. 메인에서 개발자의 방향성과 핵심 역량을 파악한다.
2. 회사·개인 프로젝트를 탐색한다.
3. 프로젝트 개요에서 기간, 역할, 기술, 담당 범위를 확인한다.
4. 모듈별 요약과 주요 작업을 살펴본다.
5. 필요한 경우 상세 구현 내용과 설계 자료를 펼쳐본다.

## 3. 정보 구조 및 라우팅

```text
/
├── /about
├── /experience/[company-slug]
├── /projects
├── /projects/[project-slug]
├── /projects/appintos
└── /projects/portfolio
```

사이드바에는 회사명과 재직 기간을 표시한다. 회사 페이지에는 해당 기간의 프로젝트 목록을, 개인 프로젝트 메뉴에는 앱인토스 앱과 포트폴리오 프로젝트를 표시한다.

## 4. 페이지 요구사항

### 메인 페이지

- 이름과 한 줄 소개
- 개발자로서의 방향성
- 핵심 역량
- 주요 기술 스택
- 경력 요약
- 대표 프로젝트 링크

소개 문장은 기술명 나열보다 업무 단위의 역량을 중심으로 작성한다.

- 웹 서비스 기능 설계 및 구현
- 관리자·운영 시스템 개발
- 공통 모듈과 도메인 기능 개발
- 인증·권한 처리
- 데이터 처리 및 배치 자동화
- 기존 시스템 유지보수와 개선
- 결제 기능 및 업무 흐름 구현

### 경력·프로젝트 목록

- 회사명, 재직 기간, 프로젝트명, 프로젝트 기간 표시
- 회사 프로젝트와 개인 프로젝트 구분
- 공개 제한 프로젝트는 공개 가능한 범위만 노출
- 프로젝트 상세 페이지로 이동할 수 있는 명확한 링크 제공

### 프로젝트 상세 페이지

상단에서 10~20초 안에 프로젝트의 성격과 담당 범위를 파악할 수 있어야 한다.

- 공개용 프로젝트명
- 실제 프로젝트명 또는 `공개 제한` 표기
- 한 줄 설명
- 진행 기간
- 담당 역할
- 사용 기술
- 담당 범위
- 핵심 기여 또는 주요 결과

이후 다음 순서로 콘텐츠를 제공한다.

1. 프로젝트 개요
2. 모듈별 요약
3. 주요 작업
4. 상세 내용 및 설계 자료

### 주요 작업 콘텐츠 형식

커밋을 그대로 나열하지 않고 문제 해결 사례로 재구성한다.

- 작업 제목
- 문제
- 고려사항
- 담당 작업
- 기술적 접근
- 결과
- 관련 기술 및 모듈

정량적 효과가 실제 자료로 확인되지 않으면 임의의 수치를 작성하지 않는다. 대신 구현 범위, 개선한 구조와 영향받은 업무 흐름을 정확히 표현한다.

## 5. 콘텐츠 모델

초기에는 프로젝트별 MDX 파일 하나에 프로젝트 개요와 주요 작업을 함께 작성한다.

```text
content/
├── companies/
│   ├── company-a.mdx
│   └── company-b.mdx
├── projects/
│   ├── shopping-platform.mdx
│   ├── ehdb.mdx
│   ├── appintos.mdx
│   └── portfolio.mdx
└── experiences/
```

권장 frontmatter:

```yaml
---
title: 상가 운영 플랫폼
slug: shopping-platform
company: 회사 A
period: 2023–2025
visibility: anonymized
role: 웹 개발
technologies:
  - React
  - Next.js
  - Spring
  - PostgreSQL
modules:
  - 공통 기반
  - 결제
  - 매장 관리
  - 관리자
---
```

공개 등급은 다음 기준을 사용한다.

- `public`: 프로젝트명, 화면과 상세 내용 공개 가능
- `anonymized`: 도메인과 역할만 공개하고 회사·고객·서비스명 익명화
- `restricted`: 개요와 담당 범위만 공개
- `private`: 포트폴리오에 노출하지 않음

## 6. 원본 자료와 공개 콘텐츠 분리

```text
Notion
  → 커밋 기록, 작업 메모, 조사 자료

MDX
  → 공개 범위 검토와 익명화를 거친 콘텐츠

Next.js
  → 방문자에게 콘텐츠 표시
```

Notion을 실시간으로 그대로 공개하지 않는다. Notion은 원본 자료로 유지하고, 공개할 내용은 검토·익명화·큐레이션하여 MDX에 반영한다.

## 7. 기술 요구사항

- Framework: Next.js
- Routing: App Router
- Language: TypeScript
- Styling: Tailwind CSS
- Content: MDX
- Image: `next/image`
- Deployment: Vercel Hobby 우선 검토
- Database: 초기에는 사용하지 않음

### 컴포넌트 실행 위치

- 서버 컴포넌트: 프로젝트 목록·상세, MDX 렌더링, 파일 기반 콘텐츠 조회
- 클라이언트 컴포넌트: 모바일 메뉴, 아코디언, 검색·필터 등 브라우저 상호작용

정적 콘텐츠도 기본적으로 서버 컴포넌트로 구성한다. 컴포넌트 구분 기준은 DB 사용 여부가 아니라 브라우저 상호작용 필요 여부다.

## 8. Figma 및 이미지 자료

Figma는 구현 전 화면·사용자 흐름·상태를 검토한 설계 근거로 활용한다.

기본 공개 방식은 민감한 내용을 제거한 PNG/WebP export다.

```text
public/projects/[project-slug]/
├── flow.webp
├── admin-dashboard.webp
└── mobile-screen.webp
```

공개 가능한 별도 사본에 한해 Figma 링크를 제공할 수 있다. 회사 원본 파일 embed는 로그인·권한·민감 정보 노출 문제 때문에 초기 기본 방식으로 사용하지 않는다.

Figma MCP는 런타임 의존성이 아닌 콘텐츠 정리와 디자인 분석을 위한 선택적 보조 도구로 사용한다.

## 9. 데이터베이스 및 운영 정책

초기에는 DB 없이 Git과 MDX로 관리한다. 포트폴리오는 콘텐츠 중심의 정적 사이트이므로 별도 관리자·인증·백업·마이그레이션 비용을 만들지 않는다.

다음 요구가 생길 때 CMS 또는 DB를 검토한다.

- 웹 관리자 화면에서 콘텐츠를 직접 편집해야 하는 경우
- 여러 사용자가 로그인하여 문서를 관리해야 하는 경우
- 댓글·문의·조회수 등 데이터를 저장해야 하는 경우
- 콘텐츠 규모가 크게 증가하는 경우
- 실시간 외부 데이터 연동이 필요한 경우

확장 순서:

1. MDX 유지
2. Notion을 빌드 시점 CMS처럼 사용
3. Sanity·Contentful·Strapi 등 Headless CMS 검토
4. 필요할 때 직접 DB와 관리자 페이지 구축

## 10. 비기능 요구사항

- 모바일·태블릿·데스크톱 반응형 지원
- 키보드로 주요 UI 조작 가능
- 명확한 heading 계층과 링크 구조
- 이미지 최적화 및 적절한 대체 텍스트
- 상세 내용은 기본 접힘 상태로 두어 정보 밀도 조절
- 공개 제한 자료의 익명화 기준 준수
- 빌드 및 린트 오류 없이 배포 가능
- 개인 도메인 연결 전 Vercel 기본 도메인에서 검증

## 11. 구현 단계

### 1단계: 기본 뼈대

- Next.js App Router 프로젝트 생성 완료
- 기본 layout과 page 확인
- Tailwind 및 TypeScript 동작 확인
- Git 저장소와 문서 구조 구성

### 2단계: 레이아웃

- 공통 layout 구현
- 사이드바와 모바일 메뉴 구현
- 메인 페이지 기본 구성
- 색상·타이포그래피·간격 등 디자인 토큰 정리

### 3단계: 대표 콘텐츠

- 대표 회사 프로젝트 1개 선정
- 주요 작업 2~4개 작성
- 프로젝트 개요와 모듈 카드 구현
- 아코디언 기반 상세 내용 구현

### 4단계: 콘텐츠 확장

- 회사별 경력 페이지 추가
- 대표 프로젝트 3~5개로 확장
- 앱인토스 프로젝트 추가
- 포트폴리오 프로젝트 자체 소개 추가
- Figma export 이미지 선별 및 익명화

### 5단계: 품질 및 배포

- 반응형 검증
- 키보드 접근성 검토
- 링크·이미지·metadata 검증
- `npm run lint` 및 production build 검증
- Vercel 배포
- 개인 도메인 연결

## 12. 초기 완료 기준

- `/`에서 이름, 방향성, 핵심 역량과 대표 프로젝트를 확인할 수 있다.
- 사이드바에서 회사·개인 프로젝트를 탐색할 수 있다.
- 대표 프로젝트 상세 페이지에서 개요, 역할, 기술, 모듈과 주요 작업을 볼 수 있다.
- 주요 작업의 상세 내용을 접었다 펼칠 수 있다.
- 모바일 화면에서도 주요 콘텐츠와 메뉴를 사용할 수 있다.
- 회사 기밀 및 공개 불가 정보가 포함되지 않는다.
- 린트와 production build가 성공한다.
- 배포된 주소에서 모든 핵심 라우팅이 정상 동작한다.

## 13. 우선순위

1. 공개 범위와 익명화 기준 확정
2. 메인 페이지 및 사이드바 구현
3. 대표 프로젝트 1개 콘텐츠 작성
4. 프로젝트 상세 UI 구현
5. 모바일 메뉴·상세 아코디언 구현
6. 대표 프로젝트 3~5개로 확장
7. 개인 프로젝트 추가
8. 이미지·Figma 자료 추가
9. 검색·필터 등 사용성 개선
10. 배포 및 도메인 연결
